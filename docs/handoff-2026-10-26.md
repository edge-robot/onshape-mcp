## Build and deployed image

Deployed: `localhost/clawonshape-mcp:cc67472-goal-grant-curl` @ `sha256:4e788a35…c45d`. Full digests and
the binary hash are in the contract §9 row and in clawonshape
`docs/evidence/2026-10-21-goal-workflow-live-acceptance.md`. It was produced in two steps:

1. **Distroless build** from `cc67472` with the fork [`Containerfile`](../Containerfile), target `runtime`
   (static musl release binary, `--locked`, toolchain from `rust-toolchain.toml`):
   `podman build --target runtime -t localhost/clawonshape-mcp:cc67472-goal-grant .`
   → `sha256:0dd5ec35…acfcf`, binary sha256 `4dca4cde…07a2cf`.
2. **curl wrapper.** The Clawake quadlet `HealthCmd` is still `curl --fail …/health` with
   `HealthOnFailure=kill`, and distroless has no curl (97 restarts on 2026-10-20). The binary is copied
   unchanged out of step 1 and wrapped by clawonshape
   [`deploy/onshape-mcp/Dockerfile`](https://github.com/edge-robot/clawonshape/blob/feat/21-work-context-selection/deploy/onshape-mcp/Dockerfile)
   (digest-pinned Debian trixie-slim + `curl`, UID 1000). The result is tagged `-curl`.

Reproducible rebuild for a successor:

```sh
git clone https://github.com/edge-robot/onshape-mcp.git src && git -C src checkout --detach <commit>
podman build --target runtime -t localhost/clawonshape-mcp:<sha>-goal-grant src
cid=$(podman create localhost/clawonshape-mcp:<sha>-goal-grant)
mkdir ctx && podman cp "$cid:/usr/local/bin/onshape-mcp" ctx/ && podman rm "$cid"
sha256sum ctx/onshape-mcp            # compare with the binary hash in the §9 row
cp src/LICENSE-MIT src/LICENSE-APACHE ctx/
cp <clawonshape>/deploy/onshape-mcp/Dockerfile ctx/
podman build -t localhost/clawonshape-mcp:<sha>-goal-grant-curl ctx
```

The `rust` and `distroless` base images in the `Containerfile` are pinned by tag, not by digest. A different
binary hash on rebuild is therefore a finding to explain, not proof of a source change (contract G11).
Once Clawake switches to `HealthCmd=/usr/local/bin/onshape-mcp healthcheck` (clawake#39), drop step 2.
To ship the #6 fix, rebuild from `1226c6b` or later. That is a new image and needs a live E2E (§9 order).

## Open issues

- **#6 RUSTSEC-2026-0382** (rustls-webpki 0.103.15, distrusted emSign intermediates): fixed in the lockfile
  only (`1226c6b`, 0.103.16). The deployed `cc67472` binary is still affected until it is rebuilt.
  `cargo deny check` still fails on **RUSTSEC-2026-0386** (tokio 1.53.2, `AsyncFd` constructors unsound;
  fix `>=1.53.3`). That advisory was already present at `cc67472`. The workspace does not use `AsyncFd`.
  Upstream is on tokio 1.54.0.
- **#7 private-file hardening** (`crates/onshape-mcp-io/src/external_token.rs`, `private_json`), not fixed:
  - `open` uses `custom_flags(0x20000)`, which is `O_NOFOLLOW` only on x86_64 (and the generic
    ABI). On aarch64, arm and powerpc the value differs (aarch64: `0x20000` is `O_LARGEFILE`), so the
    final-component no-follow guard silently drops there. This affects every file read through
    `private_json`: the token file, the approval file and the goal grant. `dispatch_journal.rs` defines its
    own `O_NOFOLLOW` with an aarch64 branch, but its fallback is also wrong for arm and powerpc. The
    deployed image is x86_64 musl, so it is not affected.
  - The canonical check `std::fs::canonicalize(p)? != p` compares `Path` values. `Path` equality ignores
    interior `.` segments, repeated `/` and a trailing `/`, so non-canonical spellings pass. Symlinks in
    the path still change the result and are rejected. In addition, `validate_config` requires only
    `is_absolute()` for `file` and `mutation_approval_file`. `goal_grant_file` and `dispatch_journal_dir`
    use the strict byte check `canonical_absolute`.
- **#9 selected-context reads** (parked): selection beyond the bound element (other Part Studios,
  documents) needs per-selection MCP target provisioning. The target is static
  (`document_id`/`workspace_id`/`element_id` in `[external_token]`; contract G3). Increment 1 of
  clawonshape#21 needed no server change (clawonshape ADR, "Review outcome and increment 1").

## Upstream delta risk

As of the fetch on 2026-10-26, `feat/5-goal-grant` is **29 commits behind** `altendky/main` (`1691cb3`) and
55 ahead of the base `f78ddc4`. The upstream commits are dependency and CI updates (15 files, among them

`crates/onshape-mcp-io/src/lib.rs` (+320 lines) and `crates/onshape-client-io/src/lib.rs`, so an rmcp bump
may conflict there. Rebase or merge only with the full test suite and a new live E2E. This branch is
fork-only and is not offered upstream as a whole.

## Onshape REST quota

Every upstream API call counts against the plan's annual cap (2,500 calls per year; about 800 used by
2026-10-26, clawonshape ADR-2026-10-26). **The server has no call accounting.** A per-request counter
belongs at:

- `crates/onshape-client-io/src/lib.rs`, `OnshapeClient::execute`, just before `builder.send()`. This is
  the one choke point for API calls in every mode. Note that the OAuth modes in
  `crates/onshape-mcp-io/src/lib.rs` (`execute_oauth_inner`, `execute_http_oauth_raw`) retry once after a 401,
  which costs a second call.
- or, scoped to external-token mode, `crates/onshape-mcp-io/src/external_token.rs`, `Dispatcher::execute`.

Token exchanges in `login.rs` and `oauth_server.rs` call reqwest directly and bypass this point.
`onshape_auth_status` with `validate: true` and every `onshape_api_call` count. `onshape_api_search`,
`onshape_api_explain` and `onshape_api_schema` are local (embedded OpenAPI spec). Not implemented, by decision.
